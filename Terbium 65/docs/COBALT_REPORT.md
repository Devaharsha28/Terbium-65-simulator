# Cobalt — Complete Architecture & ISA Report

A complete **balanced-ternary CPU** built entirely out of Terbium 65
logic gates, expressed as hierarchical chip JSON. No simulator
modifications — the CPU is ~4,500 chips of ordinary 1-trit logic,
generated by `Tools/cobalt/` and verified against a Python emulator.

---

## 1. What is balanced ternary here?

Every wire carries **trits**: `-1`, `0`, `+1` (displayed `-`, `0`, `+`).
A "9-trit bus" packs 9 trits into one pin — a signed number in
**−9841 … +9841** (since 3⁹ = 19683, half is 9841).

```
value of trits t8..t0 = t8·3⁸ + t7·3⁷ + ... + t0·3⁰     (each ti ∈ {-1,0,+1})
```

Examples: `[+1,0,0,...]` = +1, `[-1,-1,...,-1]` = −9841,
`[0,0,...,0]` = 0.

Pin widths used: **1 trit** (control), **3 trits** (small fields/addresses),
**9 trits** (data words).

## 2. How the CPU was made

```
Tools/cobalt/
  isa.py        — assembler + emulator (ground truth for behavior)
  chips.py      — JSON chip builder (pins, subchips, wires, layout, routing)
  blocks.py     — leaf arithmetic chips (ADDER9, SUB9, CMP9, MUX2, ...)
  blocks2.py    — ALU, CTRL, EXEC, REGFILE, RAM27, COBALT, COBALT_SYS
  csim.py       — Python replica of the Unity simulator (runs the JSON)
  gen_cobalt.py — builds the "Cobalt" project (demo program baked in)
  test_*.py     — block tests + hardware-vs-emulator comparisons
  validate.py   — JSON schema + unconnected-input lint
```

Workflow: `python gen_cobalt.py` → emits `Chips/*.json` + project files →
`csim` simulates the real JSON → compared instruction-by-instruction
against `isa.Machine`. 33-instruction regression suite: **all match**.

Why gates and not a "CPU chip": the simulator has no CPU primitive —
everything must be built from the existing gate/memory/ROM library.

## 3. Machine architecture

### 3.1 Block diagram (COBALT_SYS = COBALT + ROM)

```
                 ┌──────────────────────────── COBALT_SYS ────────────────────────────┐
                 │                                                                    │
  RESET MODE ───►│  COBALT core                              PROGRAM (ROM 19683x9)     │
  STEP     ────►│   ┌────────┐   ┌─────────┐   ┌───────┐   ┌────────┐                │
                │   │ PC0-8  │──►│ INSTR/   │──►│ EXEC  │   │        │                │
                │   │ + PC   │   │ RA/RB_SEL│   │       │   │  PC ──►│ ADDRESS        │
                │   └────────┘   └─────────┘   │ DECODE│   │        │                │
                │   ┌────────┐                 │ ALU   │   │ DATA ─►│ INSTR ────────►│
                │   │REGFILE │◄── RA/RB ──────►│ CTRL  │   └────────┘                │
                │   │27×9tr  │                 │ stage │                            │
                │   └────────┘                 │ regs  │                            │
                │   ┌────────┐                 └───┬───┘                            │
                │   │ RAM27  │◄── LDA/STR ────────┘                                │
                │   │27×9tr  │                                                     │
                │   └────────┘                                                     │
                │   PHASE/BOOT/FLAG/CARRY/HALT state + WB glue                      │
                └────────────────────────────────────────────────────────────────────┘
```

### 3.2 The two-phase machine

The simulator evaluates gates in **arbitrary order each frame**, so a
naive `reg = reg+1` races itself. Cobalt solves this with an explicit
**phase flip-flop** (the `PH` MEM + `PHASE` output):

| PHASE | meaning | what happens |
|---|---|---|
| `−1` | **EXEC** | DECODE/ALU/CTRL compute the *next* instruction's effects; stage MEMs capture the result bundle |
| `+1` | **WB** (writeback) | stage MEMs' contents are committed to REGFILE, RAM27, PC, FLAG, CARRY, HALT |

- `EXEC_EN = +1` only during EXEC → stage regs latch then, hold during WB.
- `WB_pos` qualifies every write-enable → writes are atomic on the WB edge.
- `BOOT` MEM guards power-on so PH can't latch a dead state on frame 1.
- Manual mode: `STEP` pin toggles phases (~50% per press — press until
  `PHASE` flips, then wait ~40 frames for the deep EXEC cone to settle).
- Auto mode: `MODE=+1` → internal `CLOCK` (500-frame period) drives phases
  through `PULSE` → ~1 instruction/second.

### 3.3 Instruction lifecycle (one instruction)

```
PC ──► ROM.ADDRESS ──► INSTR (9 trits) ──► DECODE ──► 44 opcode lines
                          │                            │
                          ├──► RA_SEL/RB_SEL ──► REGFILE read ports ──► RA9, RB9
                          │
                          └──► EXEC: DECODE + ALU + CTRL
                                   ALU:  RA9,RB9,IMM → RES9,FLAG,CARRY
                                   CTRL: NEXTPC9, WR_EN, WR_ADDR, *_WE, HALT
                                       │
                            stage MEMs (NEXTPC0-8, WRDATA0-8, ...)
                                       │  (latched during EXEC)
WB phase ──► REGFILE write, RAM write, PC←NEXTPC, FLAG/CARRY/HALT commit
```

## 4. The ISA

### 4.1 Instruction word format

```
trit index:  8   7   6   5  |  4   3  |  2   1   0
field:      o3  o2  o1  o0 |  A hi A lo|  X2  X1  X0
            └── opcode ────┘  └─ A ───┘  └── X ──┘
```

- **opcode** = trits T8,T7,T6,T5 = `(o3,o2,o1,o0)` — written below as a
  4-trit pattern `(-,-,-,-)` etc.
- **A field** = T4,T3 → 2-trit signed value −4…+4 → **active register**.
- **X field** = T0,T1,T2 → 3-trit signed value −13…+13 → **general
  register** (most ops) **or small immediate** (imm/shift/LDI forms).

### 4.2 Registers

| file | range | count | role |
|---|---|---|---|
| active | r-4 … r4 | 9 | ALU A-operand, LDI target, STR addr, jump offsets |
| general | r-13 … r13 | 27 | ALU B-operand, LDA addr, MOV data, jump-test |

`MOV.AG rA, rX` : `active[A] ← general[X]`
`MOV.GA rA, rX` : `general[X] ← active[A]`

### 4.3 ALU instructions — opcode o3 = −1

All write `rA ← f(rA, operand)` except CMP (writes FLAG).
`rX` = general reg; **imm** form uses X field as 3-trit immediate.

| opcode trits | mnemonic | reg | imm | semantics |
|---|---|---|---|---|
| `(-,-,-,-)` | ADD | ✓ | ✓ | rA = rA + rX (ternary add, carry→CARRY) |
| `(-,-,0,-)` | SUB | ✓ | — | rA = rA − rX |
| `(-,-,+,-)` | MUL | ✓ | — | per-trit multiply: rA[i]·rX[i] |
| `(-,0,-,-)` | MIN | ✓ | — | rA[i] = min(rA[i], rX[i]) per trit |
| `(-,0,0,-)` | MAX | ✓ | — | per-trit max |
| `(-,0,+,-)` | CONS | ✓ | ✓ | rA[i] = rA[i] if == rX[i] else 0 ("consensus") |
| `(-,+,-,-)` | ANY | ✓ | ✓ | per-trit clamp-sum |
| `(-,+,0,-)` | IS | ✓ | ✓ | rA[i] = +1 if equal else −1 |
| `(-,+,+,-)` | CMP | ✓ | ✓ | FLAG = sign(rA − rX): −1/0/+1 |

### 4.4 Shift instructions — o3 = 0, o2 = −1 or 0

`rA ← shift(rA, amount)`; amount = low 3 trits of rX (reg) or imm.

| opcode trits | mnemonic | reg | imm | direction |
|---|---|---|---|---|
| `(0,-,-,-)` | SHL | ✓ | ✓ | shift left (toward MSB) |
| `(0,-,0,-)` | SHR | ✓ | ✓ | shift right |
| `(0,-,+,-)` | RL | ✓ | ✓ | rotate left (wraps) |
| `(0,0,-,-)` | RR | ✓ | ✓ | rotate right |

### 4.5 Data movement — o3 = 0, o2 = 0 or +

| opcode trits | mnemonic | format | semantics |
|---|---|---|---|
| `(0,0,0,-)` | HALT | — | stop CPU; PC write-back gated off |
| `(0,0,0,0)` | NOP | — | nothing (also all reserved opcodes) |
| `(0,0,+,-)` | LDI.L | rA, imm3 | rA = imm in trits 0–2, **trits 3–8 = 0** |
| `(0,0,+,0)` | LDI.M | rA, imm3 | patch trits 3–5, keep rest |
| `(0,0,+,+)` | LDI.H | rA, imm3 | patch trits 6–8, keep rest |
| `(0,+,-,-)` | MOV.AG | rA, rX | active[A] ← general[X] |
| `(0,+,-,+)` | MOV.GA | rA, rX | general[X] ← active[A] |
| `(0,+,0,-)` | LDA | rA, rX | rA ← RAM[low3(rX)+13] |
| `(0,+,0,+)` | STR | rA, rX | RAM[low3(rA)+13] ← rX |

> **LDA/STR asymmetry**: LDA takes its address from a **general** reg's
> low 3 trits; STR takes it from an **active** reg's low 3 trits.
> Data for STR must be a general reg.

### 4.6 Jumps — o3 = +1 (PC-relative to *current* instruction)

Two families:

**F2 — flag/carry conditions**, offset = imm5 (low 5 trits, −121…+121):

| opcode trits | mnemonic | condition |
|---|---|---|
| `(1,-,-,-)` | JL | FLAG = −1 |
| `(1,-,-,0)` | JE | FLAG = 0 |
| `(1,-,-,+)` | JG | FLAG = +1 |
| `(1,-,0,-)` | JCN | CARRY = −1 |
| `(1,-,0,0)` | JCZ | CARRY = 0 |
| `(1,-,0,+)` | JCP | CARRY = +1 |
| `(1,-,+,0)` | JMP | always |
| `(1,0,-,-)` | JGE | FLAG ≥ 0 |
| `(1,0,-,0)` | JNE | FLAG ≠ 0 |
| `(1,0,-,+)` | JLE | FLAG ≤ 0 |

**F1 — register test**, offset = **full 9-trit value of rA** (huge range):

| opcode trits | mnemonic | condition on rX |
|---|---|---|
| `(1,+,-,-)` | JN | rX < 0 |
| `(1,+,-,0)` | JZ | rX = 0 |
| `(1,+,-,+)` | JP | rX > 0 |

### 4.7 Encoding example — `ADD r1, r2`

```
A field: r1 → 2-trit value +1  → trits T4,T3 = (+1, 0)
X field: r2 → 3-trit value +2  → trits T2,T1,T0 = (−1,+1,0)
opcode:  ADD reg = (−,−,−,−)   → trits T8..T5 = (−1,−1,−1,−1)

word (T0→T8):  −1, +1, 0, +1, 0, −1, −1, −1, −1
ternary str (MSB first): ----0+0+-     decimal: −9691
```

## 5. Hardware implementation of each instruction

All instructions share the same physical path — the opcode only changes
*which* control lines fire:

| stage | hardware |
|---|---|
| fetch | PC9 → ROM.ADDRESS; ROM.DATA → INSTR bus |
| decode | DECODE chip: per opcode, 4× `ISN` equality + `MIN` + `CLU` → one-hot line |
| operand read | RA_SEL/RB_SEL (from INSTR fields) → REGFILE read ports → RA9, RB9 |
| execute | ALU picks result by opcode line (tri-state mux): ADDER9/SUB9/CMP9/MIN9/MAX9/MUL9/CONS9/ANY9/IS9/SHIFT9/LDI-merge/MOV/LDA passthroughs |
| control | CTRL: NEXTPC = PC + OFF (OFF = 1, imm5, or rA value; gated by jump-taken logic) + all write-enables + HALT |
| stage | EXEC's 29 stage MEMs latch the result bundle while PHASE=−1 |
| commit | WB phase: REGFILE/RAM27/PC/FLAG/CARRY/HALT write enables fire |

Special cases:
- **LDI.L/M/H**: ALU builds the constant bus (imm trits placed in the
  right positions, zeros elsewhere); LDI.L additionally zeroes upper trits.
- **MOV/LDA/STR**: mostly wiring — ALU passes RA/RB/RAMD through; CTRL
  sets WR_ADDR = A-field (MOV.AG) or X-field (MOV.GA), RAM_WE for STR.
- **Jumps**: CTRL computes `TAKEN` (OR of opcode-line ∧ condition) and
  `OFF_FINAL`; ADDER9 adds PC+OFF → NEXTPC.
- **HALT**: sets the HALT MEM; PC write-enable is gated by `~HALT`
  forever after.

## 6. Memory map

| space | size | addressing |
|---|---|---|
| ROM (program) | 19,683 × 9 trits | PC value −9841…+9841 → row = PC+9841; **program at rows 0+** |
| RAM | 27 × 9 trits | cell = low3(reg)+13 → cells 0–26 ↔ values −13…+13 |
| Registers | 27 × 9 trits | r-13…r13; ALU-visible: r-4…r4 |

PC powers up at **−9841** (= all `-` trits) so fetch #1 reads ROM row 0.
The `PC` output pin shows the signed value (−9841, −9840, … climbing
toward 0 and beyond).

## 7. How to enter & run programs

1. Open project **Cobalt**, place **COBALT_SYS** (COBALT+ROM pre-wired)
   or wire your own: `COBALT.PC → ROM.ADDRESS`, `ROM.DATA → COBALT.INSTR`.
2. Double-click the `ROM 19683x9` (label `PROGRAM`) → edit menu.
3. Enter words at **rows 0,1,2,…** — TERNARY mode (9 chars `-`/`0`/`+`,
   MSB first) or DECIMAL mode (signed value).
4. Drive `RESET=+1` ~2 frames, release. Then:
   - **Manual**: `MODE=0`, tap `STEP` until `PHASE` flips each press;
     wait ~40 frames per phase.
   - **Auto**: `MODE=+1` → ~1 instr/sec.
5. Watch outputs: `PC`, `R-13`…`R13`, `FLAG`, `CARRY`, `PHASE`, `HALTED`.

Assembler + emulator for development: `Tools/cobalt/isa.py`
(`assemble_program`, `Machine`). Example programs:
`docs/programs/00-basics.md`, `docs/programs/01-bubble-sort.md`.

## 8. Known limitations

- **Speed**: ~1 instr/sec auto (500-frame phases × 2, ~4,500 gates
  evaluated per frame). Manual stepping needs settle waits.
- **RAM/registers are small** (27 cells each) — by design for the
  balanced-ternary address space demo.
- **Jumps are PC-relative** with ±121 (imm5) or full-register range
  (jump_reg) — no absolute jumps.
- Reserved opcodes (37 of 81) decode as NOP.
- `MUL`/`MIN`/`MAX`/`SUB`/shifts are register-only (no imm form).
